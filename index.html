Pick the sandbox: gVisor or MicroVM

          
Agent Substrate offers both as first-class sandbox classes. They sit at different points on the
          isolation-versus-overhead line, and the right pick depends on the workload the agent will run.

        

        

          

            
gVisor

            
userspace kernel · runsc · Sentry

            
An application kernel that implements a Linux-like interface. It is written in Go — a
            memory-safe language — and runs in userspace. Its core piece, the Sentry, sits between the container
            and the real kernel, intercepting and answering system calls itself, so untrusted agent code never
            talks to the host kernel directly. It ships as runsc, an OCI runtime that integrates with
            Docker and Kubernetes.

            
    
              
  • Runs anywhere: any standard Linux node — no /dev/kvm required.
    • 
              
  • Middle path: not a VM and not just a syscall filter like seccomp — VM-grade isolation thinking at container density and speed.
    • 
              
  • Compatibility gap: the Sentry doesn't implement every Linux syscall, so some workloads won't run.
    • 
              
  • Limits caveat: per-container resource limits aren't enforced inside the sandbox.
    • 
              
  • Provenance: Google donated gVisor to the CNCF as a Sandbox project in October 2026.
    • 
            

            
Choose gVisor when You want strong isolation on ordinary nodes, fast startup, and high sandbox density — and your agent's toolchain sticks to common syscalls.

            
          


          

            
MicroVM

            
KVM guest · Kata Containers · Cloud Hypervisor

            
Each sandbox is a real KVM virtual machine — a Kata Containers guest on Cloud
            Hypervisor with its own guest Linux kernel. That buys near-total Linux compatibility: there is no
            missing-syscall problem, because the agent's code talks to a genuine kernel, just not the host's.

            
    
              
  • Hardware requirement: a Linux node with /dev/kvm, requested as the ate.dev/kvm device resource.
    • 
              
  • Real limits: per-container limits are enforced via guest cgroups — a container that blows its memory limit is OOM-killed on its own while siblings in the actor keep running.
    • 
              
  • Sizing: minimum memory is 128 MiB; CPU comes from actual vCPUs — a 500m actor boots with 1 vCPU and gets half a CPU of host time.
    • 
              
  • Snapshots: state lives on the host filesystem, shared into the guest over virtio-fs, and saved as tar archives.
    • 
            

            
Choose MicroVM when The agent runs arbitrary or syscall-heavy code, needs hard per-container resource enforcement, or must behave exactly like a real Linux machine.

Before you run it for real

          
    
            
  • Tooling: Docker, kubectl, kind, and the ax CLI installed locally.
    • 
            
  • For gVisor: nothing special — runsc is installed onto nodes by the Substrate setup in commands.sh.
    • 
            
  • For MicroVM: at least one node with /dev/kvm exposed and labeled so Substrate can schedule the ate.dev/kvm device; memory requests must be at least 128 MiB.
    • 
            
  • Network: the default policy is fully isolated. Loosen it to egress-only only if the agent genuinely needs to call external APIs.
    • 
            
  • Replication: 1 replica is enough for a kind rehearsal; run 3 replicas in production so the agent survives a node loss. Every replica is a full sandbox, so budget replicas × the per-agent CPU and memory — and, for MicroVM, one ate.dev/kvm device per replica.
    • 
          

        

      


      
      

        

          
Production notes

          
What to know before running this for real — the gaps between a kind rehearsal and a production
          deployment, and the places where gVisor and MicroVM behave differently than the YAML suggests.

        

        

          

            
Note 01 · Availability

            
Replicas on kind aren't real redundancy

            
In kind, every “node” is a Docker container on one host — 3 replicas there protect you from a
            crashed agent, not a crashed machine. For actual high availability, spread replicas across real
            nodes with anti-affinity / topology spread in a real cluster.

          

          

            
Note 02 · Capacity

            
Keep headroom, not just copies

            
With 3 replicas on capacity for exactly 3, losing one leaves you at zero spare. If uptime
            matters, size for N+1 — enough room to run one extra replica while one is down or updating.

          

          

            
Note 03 · Sizing

            
Size MicroVM in whole vCPUs

            
Agent Substrate rounds MicroVM CPU up to whole vCPUs (minimum 1, minimum 128 MiB memory), so
            asking for 500m still boots a 1-vCPU guest. Fractional sizes are fine on gVisor; on MicroVM
            they quietly cost more than you asked for.

          

          

            
Note 04 · Limits

            
Don't lean on per-container limits under gVisor

            
That class accepts per-container limits but ignores them at runtime — watch actual usage
            at the pool level. MicroVM enforces limits in the guest, which is one reason to pick it for noisy
            workloads.

          

          

            
Note 05 · Security

            
Fence the network and the secrets

            
Default-deny egress with an allowlist (model APIs, package registries, nothing else) — a
            sandboxed agent with open internet is still an exfiltration risk. Keep tokens out of the YAML and
            the image; inject them as secrets at runtime.

          

          

            
Note 06 · State

            
Replicas aren't backups

            
Use AX's checkpoint/suspend for idle agents instead of paying to keep copies warm,
            snapshot on a schedule, and actually test a restore — the formats differ (runsc
            checkpoint bundles for gVisor, tar via virtio-fs for MicroVM), so verify yours works before you
            need it.

          

          

            
Note 07 · Compatibility

            
Test your workload under gVisor early

            
Its Sentry doesn't implement every syscall; debuggers, FUSE, and low-level networking tools are
            the usual casualties. If something breaks there, that's the signal to move that agent to
            MicroVM.

Glossary — plain language

      

        
Actor
The unit Substrate schedules and keeps alive — your agent plus its sandboxes, treated as one thing.

        
WorkerPool
The pool of worker nodes/slots Substrate draws from when an actor needs a sandbox.

        
SandboxClass
A named recipe (gVisor or MicroVM) that says how a sandbox is isolated, its runtime, and its limits.

        
Sentry
gVisor's userspace kernel. It answers the container's syscalls itself so they never reach the host kernel.

        
runsc
The OCI runtime that plugs gVisor into Docker and Kubernetes — “run sandboxed container”.

        
Kata Containers
Software that runs a container inside a lightweight VM, so it feels like a container but isolates like a VM.

        
Cloud Hypervisor
The small, fast virtual-machine monitor that actually runs the MicroVM guest on KVM.

        
virtio-fs
A fast shared folder between host and guest VM — how MicroVM state is shared and snapshotted as tar.

        
Checkpoint / snapshot
A saved copy of an agent's state you can resume from — in under a second with AX — instead of starting cold.

        
Egress fencing
Default-deny outbound network rules with an allowlist, so a sandboxed agent can only reach approved endpoints.
